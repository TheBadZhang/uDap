# SWD 性能基准（STM32F411 目标）

本文件记录本 DAP 固件在 **STM32F411CEU6** 目标上的烧录速度实测值，用于：
- 回归对比（改时序/DAP 代码后跑一遍，看有没有退化）
- 判断瓶颈在哪一侧（DAP 链路 vs 目标 Flash 控制器）
- 定位慢/快路径切换点

| --- | --- | --- |
| `CPU_CLOCK` | 48 MHz | CH32X035 HSI |
| `IO_PORT_WRITE_CYCLES` | 2 | |

> 本文件其余数据是 2026-09-22 那个固件版本的基线快照，**保留原值作为回归参照**，
> 但「12 MHz 起跳」的说法只对旧版本成立 —— 新版本 6 ~ 11.5 MHz 也走快路径，
> 那几档的速度会变成快路径的 ~125 KiB/s（而不再是慢路径的 ~54）。

## RAM 写入速度（本板 DAP）

纯数据搬运，**瓶颈完全在 DAP 侧的 SWD 链路**，是衡量链路性能的干净指标。

命令：

```powershell
python tools/pyocd_ram_speed.py -t stm32f411ce --sizes 64K `
    --frequencies 1000k,2000k,3000k,4000k,8000k,11500k,12000k,16000k,20000k,40000k `
    --repeats 5
```

64 KiB @ `0x20000000`，5 轮取中位数，`program` 模式（FileProgrammer）：

| SWD 请求 | 耗时 | 写入速度 | 路径 |
| --- | --- | --- | --- |
| 1 MHz | 2361.5 ms | 27.1 KiB/s | 慢 |
| 2 MHz | 1752.0 ms | 36.5 KiB/s | 慢 |
| 3 MHz | 983.6 ms | **65.1 KiB/s** | 慢（已饱和） |
| 4 MHz | 983.5 ms | 65.1 KiB/s | 慢（饱和） |
| 8 MHz | 983.5 ms | 65.1 KiB/s | 慢（饱和） |
| 11.5 MHz | 983.7 ms | 65.1 KiB/s | 慢（饱和） |
| **12 MHz** | 303.4 ms | **210.9 KiB/s** | **快（拐点）** |
| 16 MHz | 305.4 ms | 209.5 KiB/s | 快 |
| 20 MHz | 311.1 ms | 205.7 KiB/s | 快 |
| 40 MHz | 330.5 ms | 193.7 KiB/s | 快 |

补充：`--mode raw`（直调 `write_memory_block8`）在 12 MHz 下为 **215.1 KiB/s**，
比 `program` 模式快约 17%。原因是 `RamBuilder._MAX_WRITE_SIZE = 4096`，
`program` 模式按 4 KiB 分包，每包都有一次往返开销。**想测链路上限用 `--mode raw`。**

### 观察

- 慢路径从 3 MHz 起完全饱和：3/4/8/11.5 MHz 耗时差 < 0.2 ms。因为 `clock_delay`
  被钳到最小值，请求更高频率不会有任何变化。
- 快路径 12~40 MHz 全落在 194~211 KiB/s。**快路径实际 SWCLK 是固定的 ~6 MHz**，
  由指令执行时间决定，与请求频率无关，所以填 12 还是 40 MHz 结果相同；
  差别只是余量厚度。
- 12 → 40 MHz 反而略慢（210.9 → 193.7），说明请求越高余量越紧，宁可填 12。

## RAM 读写速度（Air32 MINI DAPLink）

测量日期 2026-09-22，同一颗 F411 目标。主测工具为 `tools/openocd_speed_test.tcl`，
并用 pyocd 两条路径交叉验证。这块探针的特性：

- **对 SWD 频率只有弱依赖**：1 MHz 明显偏低（~90 KiB/s），2 MHz 以上进入平台期
  （120~172）。主要瓶颈在 **USB 传输路径**，不在 SWD 时钟。这点和本板 DAP 不同
  （本板 DAP 在 3 MHz 饱和、12 MHz 起跳 2.8 倍）。
- **读写几乎对称**（读/写 = 0.96~1.06），两个方向受同一瓶颈支配。
- **块大小以 8~16 KiB 最优**，≥32 KiB 反而下降。这是本探针的独有特征。
- **吞吐本身极不稳定**：完全相同的配置，实测 85~172 KiB/s（约 2x），
  且 5 分钟冷却不能恢复（见「稳定性」）。**单次测量不可用。**

### 块大小的影响

8 MHz，每档跑两次取最大值：

| 块大小 | 写 | 读 | 读/写 |
| --- | --- | --- | --- |
| 1 KiB | 145.7 | 154.5 | 1.06 |
| 2 KiB | 164.8 | 163.7 | 0.99 |
| 4 KiB | 161.0 | 158.5 | 0.98 |
| **8 KiB** | **171.4** | **169.6** | 0.99 |
| **16 KiB** | 168.5 | 165.7 | 0.98 |
| 32 KiB | 151.9 | 148.3 | 0.98 |
| 64 KiB | 141.9 | 136.6 | 0.96 |
| 96 KiB | 128.4 | 125.8 | 0.98 |

**8~16 KiB 是最优块大小。** 1 KiB 太小（协议开销占比高），
≥32 KiB 反而下降（64→96 KiB 降了 10~13%）。这和本板 DAP 相反 ——
本板 DAP 是块越大越好（`RamBuilder._MAX_WRITE_SIZE = 4096` 反而拖慢了 program 模式）。
所以测这块探针时，**块大小比 SWD 频率更值得调**。

### 交叉验证：pyocd 同会话交替测读写

若「写」和「读」分别在两个会话里测，差异可能纯粹来自会话状态
（这块探针的会话间波动比读写差异还大）。因此在一次连接内交替执行
写-读-写-读…，用 `tools/pyocd_ram_rw_compare.py`：

```powershell
python tools/pyocd_ram_rw_compare.py -f 1000k,2000k,4000k,8000k,12000k,16000k,17500k --pairs 8
```

64 KiB @ `0x20000000`，`write_memory_block8` / `read_memory_block8`，每频率 8 组：

| SWD 请求 | 写 中位 | 读 中位 | 读/写 |
| --- | --- | --- | --- |
| 1 MHz | 96.3 KiB/s | 103.4 KiB/s | 1.07x |
| 2 MHz | 102.9 KiB/s | 120.0 KiB/s | 1.17x |
| 4 MHz | 96.2 KiB/s | 109.8 KiB/s | 1.14x |
| 8 MHz | 124.1 KiB/s | 135.8 KiB/s | 1.09x |
| 12 MHz | 98.2 KiB/s | 110.1 KiB/s | 1.12x |
| 16 MHz | 91.6 KiB/s | 104.0 KiB/s | 1.14x |
| 17.5 MHz | 95.7 KiB/s | 109.2 KiB/s | 1.14x |

重复一轮（15 组）后读/写比仍为 **0.97x / 1.19x / 1.18x**，
绝对值在 110~144 之间 —— 和 OpenOCD 主测结论一致（读≈写，平台期）。

## 稳定性：为什么单次测量不可用

同一频率连续测多次，结果会在 **~90 KiB/s 和 ~200 KiB/s 两档之间跳**，
不是逐渐退化，也不是测量噪声（会话内极差只有 1.2~1.5x）。
例如 8 MHz 写连续 8 次：

```
124.3   205.8   210.6   199.7    97.5   103.8   217.9   212.6  KiB/s
```

前 4 次和后 2 次是「快档」，中间 2 次掉到「慢档」。相同现象在 OpenOCD 主测里
表现为「每频率第 3 次偏低」（见上表）—— 不是工具差异，是探针本身的行为。

**已排除热效应**：静置 5 分钟后再测，吞吐反而更低（95.8），紧接着又跳到 138.7：

```
冷却前        : 120.33 KiB/s
静置 5 分钟后 :  95.84 KiB/s   <- 没恢复，说明不是过热降频
紧接着        : 138.73 KiB/s   <- 立刻又变快，进一步排除热
```

**已排除主机负载**：测试时无残留进程，20 核 CPU 平均负载 33%。

原因仍未定位，怀疑与 USB 主机侧调度有关（该探针为 CMSIS-DAP **v2** bulk 传输，
而本板 DAP 是 v1 HID —— v1/v2 的差异可能是原因之一）。

**结论：测这块探针必须多采样、报中位数与极差，单次结果不可用。**
这也是为什么 `pyocd_ram_speed.py` 现在会同时打印 最快/最慢/极差。

## 探针对比：本板 DAP vs Air32

| 场景 | 本板 DAP | Air32 | 胜者 |
| --- | --- | --- | --- |
| 1 MHz 写（pyocd） | 27.1 KiB/s | **96.3** KiB/s | Air32（3.6x） |
| 12 MHz 写（pyocd） | **210.9** KiB/s | 98.2 KiB/s | 本板 DAP（2.1x） |
| 12 MHz 写（OpenOCD 主测） | 115.3 KiB/s | ~158 KiB/s | Air32 |
| 16 MHz 写（OpenOCD 主测） | 122.8 KiB/s | ~164 KiB/s | Air32 |
| 峰值写（OpenOCD） | ~123 KiB/s | **~172 KiB/s** | Air32（1.4x） |
| 频率依赖 | 强（3 MHz 饱和 / 12 MHz 跳变 2.8x） | 弱（2 MHz 以上平台） | — |
| 块大小依赖 | 越大越好 | **8~16 KiB 最优** | — |
| 测量稳定性 | 稳定（极差 1.2~1.5x） | **不稳定（极差 2x）** | 本板 DAP |
| 频率上限 | ≥40 MHz | 17.5 MHz | 本板 DAP |

四个要点：

1. **低频时 Air32 快得多**（1 MHz 下 3.6x）。本板 DAP 的慢路径在 3 MHz 就饱和
   （`clock_delay` 钳位），而 Air32 不受 SWD 时钟限制。
2. **pyocd 下高频本板 DAP 反超**（12 MHz：210.9 vs 98.2），但 **OpenOCD 下 Air32 反超**（158 vs 115）。
   两个工具给出相反结论，因为它们的最优工作点不同 —— pyocd 用大块传输会碰到
   Air32 的「≥32 KiB 降速」问题，而本板 DAP 正好相反。
3. **公平对比必须各自调到最优块大小**。Air32 在 OpenOCD 下把块从 64 KiB 改成 8 KiB
   就能从 ~142 提到 ~172；本板 DAP 在 OpenOCD + 64 KiB 下只有 115~123，
   但 pyocd 大块能到 210.9 —— 说明 **OpenOCD 对大块传输的处理不如 pyocd**。
   所以「哪块探针更快」取决于工具与块大小的组合，不能只看一组配置。
   （本板 DAP 在 OpenOCD 下的小块表现未测试，暂无数据）
4. **稳定性差异很大**。本板 DAP 可重复（极差 1.2~1.5x）；Air32 有 2x 随机跳跃，
   且不受冷却影响 —— 做性能对比时要多采样。

### 观察

- **擦除恒定 ~8.1 s**（8039~8309 ms，抖动 < 3%），与 SWD 时钟完全无关。
  这是 F411 片上 Flash 控制器的固定成本，DAP 再快也压不动。
- **写入在 12 MHz 跳变 2.4 倍**（46.7 → 114.2 KiB/s），拐点位置与 RAM 完全一致。
- **校验 ~3.7 s / 133 KiB/s**，同样不随 SWD 时钟变化 —— 校验是读操作，
  受 DAP 读带宽限制（~134 KiB/s），而非目标。
- 12 → 20 MHz 写入只差 0.5%，**没有理由往上写**。

## RAM vs Flash 对比（12 MHz）

| | 写入速度 | 瓶颈 |
| --- | --- | --- |
| **RAM** | 210.9 KiB/s | DAP 侧 SWD 链路 |
| **Flash** | 114.2 KiB/s | 目标 Flash 编程时间 |
| 比值 | **1.85×** | |

Flash 写入被目标每页编程后的等待拖住，所以比纯搬运的 RAM 慢近一倍。
**要评估 DAP 链路本身，应看 RAM 数据；Flash 数据还混了目标特性。**

## 结论

### 本板 DAP（CH32X035）

1. **12 MHz 是唯一实用档位**。慢路径在 3 MHz 就饱和（RAM 65.1 / Flash 46.7 KiB/s），
   而快路径在 12 MHz 起跳（RAM 210.9 / Flash 114.2 KiB/s），12 到 40 MHz 无增益甚至略降。
   *（本条**只对 2026-09-22 那版固件成立**；新版本阈值已降到 6 MHz，
   6 MHz 起就是快路径速，不必填 12 —— 见文末「后续变更」。）*
2. **快路径实际约 6 MHz**，请求值只影响余量、不影响速度。
   快路径余量必须保留 `SWD_FAST_DELAY_NOPS=1`。
3. **Flash 擦除是硬下限**：500 KiB 场景下擦除占 ~8.1 s，是总时间的 50%（12 MHz）。
   SWD 提速只能优化写入段的 ~4.4 s。

### Air32 MINI DAPLink

4. **吞吐对 SWD 频率只有弱依赖**：1 MHz 偏低（~90），2 MHz 以上平台（~120~172）。
   瓶颈在 USB 传输路径，所以调高 SWD 频率没用。频率实际上限 17.5 MHz。
5. **块大小以 8~16 KiB 最优**，≥32 KiB 反而下降 10~13%。这比调频率更值得调。
6. **读写几乎对称**（读/写 = 0.96~1.06），两个方向受同一瓶颈支配。
7. **吞吐有 ~2x 随机跳跃**，且**已排除热效应**（静置 5 分钟不恢复）与主机负载。
   测这块探针必须多采样并报中位数 + 极差，单次数据不可用。

### 通用

6. **不要用 pyocd 报告的 `at X kB/s`**，见下节。
7. **同一工具下块大小的影响可能大于换探针**。Air32 在 OpenOCD 下 64 KiB→8 KiB 提升 21%；
   本板 DAP 在 pyocd 下 program→raw 提升 17%。做性能结论前先确认块大小已调到最优。

## 注意：pyocd 的 "at X kB/s" 不可信

pyocd 日志：

```
Erased 65536 bytes (4 sectors), programmed 51200 bytes (50 pages), identical 0 bytes (0 pages) at 23.67 kB/s
```

该速度 = `program_byte_count / (erase_time + program_time)`（见 `pyocd/flash/loader.py`
的 `_log_performance`）。当写入数据与 Flash 现有一致时，smart_flash 会跳过擦除与编程，
**分母塌掉、分子照旧**，数字虚高数倍。

判据：**出现 `Erased 0 bytes (0 sectors)` 即为跳过烧录，该速度无意义。**

| 50 KiB @12 MHz | 编程耗时 | 速度 |
| --- | --- | --- |
| 真实烧录 | 743 ms | 68.9 KiB/s |
| 跳过烧录 | — | 160.67 kB/s（虚高，实为读回带宽） |

强制真实烧录：加 `-O smart_flash=False`，或每次换一份随机数据。

## 后续变更

### 2026-09-26：快路径阈值 12 MHz → 6 MHz

上面的基线是「12 MHz 才起跳」。这个阈值其实**不是硬编码在代码里的常量**，而是
CherryDAP 的一个可配宏算出来的（`DAP/Source/DAP.c` 的 `Set_Clock_Delay()`）：

```c
#define MAX_SWJ_CLOCK(delay_cycles)  ((CPU_CLOCK/2U) / (IO_PORT_WRITE_CYCLES + delay_cycles))
if (clock >= MAX_SWJ_CLOCK(DELAY_FAST_CYCLES)) { fast_clock = 1; ... }
```

所以把 `DAP_config.h` 里的 `DELAY_FAST_CYCLES` 从默认 `0` 改成 `2`：

$$\text{阈值}=\frac{48\,\text{MHz}/2}{2+2}=6\,\text{MHz}$$

**为什么改**：快路径的实际 SWCLK 由固定指令数决定（约 6 MHz），**与请求值无关** ——
请求 6 MHz 和请求 12 MHz 拿到同一个速率。阈值留在 12 MHz 的唯一后果，是让主机填
6 ~ 11.5 MHz 时白跑慢路径。实测确认（16 KiB 块，5 轮平均）：

| SWCLK 请求 | 写 KiB/s | 读 KiB/s | 路径 |
| ---: | ---: | ---: | :--- |
| 5000 kHz | 53.3 | 45.1 | 慢（饱和） |
| 5750 kHz | 54.1 | 45.5 | 慢（饱和，最后一档） |
| **6000 kHz** | **125.4** | **121.0** | **快（拐点）** |
| 12000 kHz | 126.3 | 119.0 | 快（与 6 MHz 同速） |

反汇编交叉验证（LTO 把 `Set_Clock_Delay` 内联进了 `DAP_ProcessCommand`）：

```asm
20002460:  lui  a5,0x5b9
20002464:  addi a5,a5,-641      ; a5 = 5 999 999
20002468:  bltu a5,a4, <快路径>  ; clock > 5999999 → 快路径
```

即阈值正好是 6 000 000 Hz；慢路径的延时算法（`(d-2+7)/8`）逐字未变。

**`DELAY_FAST_CYCLES` 的第二个用途**（决定 `PIN_DELAY_FAST()` 补几个 NOP）在本工程
不受影响：`src/dap/sw_dp.c` 已把 `PIN_DELAY_FAST` 重定义为固定一个 `__NOP()`，
且上游唯二使用它的 `SW_DP.c` / `JTAG_DP.c` **未参与编译**（`xmake.lua` 只编
`DAP.c` + `DAP_vendor.c`）。所以该宏在本工程里**纯粹是阈值旋钮**，零时序副作用。

**`SWD_FAST_DELAY_NOPS=1` 的要求仍然成立**（快路径余量）—— 这一点没有变。

**顺带修的一个坑**：`tools/speed.ps1` 与 `tools/openocd_speed_sweep.ps1` 原先把
「≥12000 kHz 是快路径」**硬编码**在打印逻辑里，改阈值后它们会打出错误的路径标注。
现已改成参数 `-FastMinKhz`（默认 6000），与该宏同步。
