### 18.6 对照探针：测试方法与横向对比

本节把「本板 uDAP 以外的第三方 CMSIS-DAP 探针」的 SWD 吞吐测试集中在一处：
测试方法、四块探针的标识、以及**唯一的总表**（按频率 × 块大小 × 调试器排成矩阵）。
各探针的逐条明细不再单独列表，避免与总表重复。

#### 测试对象与接线

| 项目 | 值 |
| --- | --- |
| 目标 | STM32F411CEU6（CPUID `0x410FC241`、DBGMCU IDCODE `0x10006431` → DEV_ID `0x431`、512 KB Flash、128 KB SRAM） |
| 测试区 | 目标 SRAM `0x20000000` 起（与 18.1、18.5 同一地址，便于对比） |
| 接线 | 探针 SWCLK / SWDIO / GND 接目标，目标单独供电 |

#### 测量流程

1. 打开探针会话、`halt` 目标；
2. **整块备份**测试区，测完**逐字写回**并 `resume`，不破坏目标正在跑的程序；
3. 填充模式 `0xA5A50000 | i`（变化的 pattern，能暴露地址线/数据线问题与突发顺序错误）；
4. 每个「频率 × 块大小」组合先预热一次，再正式测 5 次；每次分别计时「写整块」与「读整块」，
   读回**逐字校验**；失败（ACK 错 / 超时 / 数据不符）记 `ok=0` 并继续；
5. 每组取**中位数**（不取平均，避免个别离群值污染）。

#### 参数与工具

| 参数 | 取值 |
| --- | --- |
| 频率 | **1~15 MHz，步进 1 MHz**（15 档） |
| 块大小 | **1 / 4 / 16 / 64 KiB**（4 档） |
| 重复次数 | 每组合 **5 次**，取中位数 |
| 工具 | **pyocd 0.45.1** 与 **OpenOCD 0.12.0**，同一块探针各扫一遍 |

两个工具都支持在**同一条会话里改频率**（pyocd 用 `probe.set_clock()`，OpenOCD 用
`adapter speed`），所以整轮扫描只连接一次，不会把反复连接的固定开销算进结果。

#### 从总表读出的结论

1. **本板 uDAP 是「三级」形状，另外三块是「多台阶缓升」。**
   uDAP：1~5 MHz 走慢路径（64 KiB 写 24→51），**6 MHz 跳 3 倍**到 151，之后 6~15 MHz
   完全平坦（151~154）—— 就是 18.1 说的快/慢路径阈值（6 MHz），且快路径的实际 SWCLK
   由指令数钉死（约 6 MHz），请求再高也不变。
   另外三块则把请求频率映射成**离散分频**，所以是多个台阶：FanX 在 10 MHz 跳
   （64 KiB 写 484→900，约 1.86×）、CH32V305 在 8 MHz 跳（254→429，1.68×）、
   Air32 同样在 8 MHz（243→269）。**对这类探针，跳到台阶之上再往上填没有收益。**
2. **本板 uDAP 在四者里最慢，差距集中在两头**：
   低频段 1 MHz（64 KiB 写）uDAP 24，其它 117~189 —— 慢路径的半周期延时太大；
   高频段 6 MHz 及以上 uDAP 151，其它 252~307 —— 快路径被约 6 MHz 的实际时钟钉住。
3. **块大小基本不影响吞吐**：四块探针、两个工具、全频段下 1/4/16/64 KiB 的差异几乎都在
   10% 以内（uDAP 最平，<2%）。**唯一明显的是 pyocd 的小块写**：uDAP 在 6 MHz 时
   1 KiB 写 383 比 64 KiB 写 261 高 **47%**，FanX 与 Air32 也是同方向（小块更快）——
   这是主机侧把多个写命令流水化的效果；反过来**小块读更慢**（要等回包）。
4. **pyocd 全面高于 OpenOCD**，比值因探针而异：约 2.0×（FanX）、1.7×（uDAP、Air32）
   （64 KiB，6~10 MHz）。原因是 OpenOCD 把在飞命令数夹在写死的 `MAX_PENDING_REQUESTS = 3`
   （`cmsis_dap.c`），而 pyocd 不设这个上限。Air32 的 `DAP_PACKET_COUNT = 100` 也改变不了
   这一点 —— 限制在主机侧，不在探针侧。
5. **读写关系**：uDAP、FanX、CH32V305 都是**读 ≤ 写**（uDAP 最典型：pyocd 64 KiB
   261 / 234），**只有 Air32 反过来**（430 / 527）。要读大块数据时 Air32 是四者里最快的。

#### 注意事项

**OpenOCD 的 1 KiB 一列不可尽信**：它内部的计时用 TCL `clock microseconds`，在 Windows 上
粒度约 **1 ms**。64 KiB 一档耗时几百毫秒、误差可忽略；1 KiB 一档只有 2~6 ms，量化误差可达
百分之几十（原始值会整齐落在 1998 / 2000 / 3001 µs 上）。**1 KiB 一档以 pyocd 的列为准。**

**pyocd 不是每块探针都能用。** CherryUSB CH32V305 在 pyocd 下扫到第一个组合（1 MHz、
先要读 64 KiB 备份）就抛 `ProbeError: Timeout reading from probe 39D9ABCD`
（调用栈在 `read_ap_multiple`，即一次大块 AP 读），**此后它的 CMSIS-DAP 命令处理再也不回包** ——
换回 OpenOCD 也是 `CMSIS-DAP command CMD_INFO failed`，连试 6 次全失败；而 USB 设备仍然正常
枚举（`Status: OK`），说明不是掉线而是固件里的命令通道卡死。**只有拔插 USB 重新上电才能恢复**
（`pnputil /restart-device` 需要管理员权限）。所以这块探针的 pyocd 一栏留空，不硬凑数据。

**接线不良的症状（容易误判成探针坏了）**：SWD 接线（尤其 GND 回流）不好时，两个工具的反应
完全不同 ——

| 工具 | 现象 |
| --- | --- |
| OpenOCD | `CMSIS-DAP Protocol Error @ 3 (wrong parity)` 或 `SWD ack not OK @ 3 JUNK`，随后 `target ... examination failed` / `Target not examined yet` / `cannot read IDR` |
| pyocd | **照常工作**（它的 CMSIS-DAP 实现里没有 parity 字样，即不校验读回奇偶位），或报 `Unexpected ACK '5'` / `Timeout reading from probe` |

所以「pyocd 能连、OpenOCD 报 parity 错」**优先怀疑接线**，别先怀疑探针 ——
本次测试里 FanX Tek 与 uDAP 两块都踩到过，重新插好线后立刻恢复。

**旧版 Air32 数据未复现**：本节先前记录过一组 Air32 数据（2026-09-22，方法不同），
系统性比本次**低 1.3~1.7 倍**（64 KiB OpenOCD：1 MHz 100.5→129、8 MHz 161→269），
且旧记录里「约 2 倍随机跳跃、静置 5 分钟不恢复」的现象本次**完全没有出现**
（同组合 5 次极差最大 20%，多数 <8%）。**推断旧数据是在 SWD 接线不良的状态下测的** ——
接线不良的典型症状正是「吞吐偏低 + 大幅随机波动」，这一点本次被实测确认过。
用本次统一方法的数据为准。

#### 附：pyocd 的 "at X kB/s" 不可信

pyocd 的烧录日志：

```
Erased 65536 bytes (4 sectors), programmed 51200 bytes (50 pages), identical 0 bytes (0 pages) at 23.67 kB/s
```

该速度 = `program_byte_count / (erase_time + program_time)`（见 `pyocd/flash/loader.py` 的
`_log_performance`）。当写入数据与 Flash 现有一致时，smart_flash 会跳过擦除与编程，
**分母塌掉、分子照旧**，数字虚高数倍。

判据：**出现 `Erased 0 bytes (0 sectors)` 即为跳过烧录，该速度无意义。**

| 50 KiB @12 MHz | 编程耗时 | 速度 |
| --- | --- | --- |
| 真实烧录 | 743 ms | 68.9 KiB/s |
| 跳过烧录 | — | 160.67 kB/s（虚高，实为读回带宽） |

强制真实烧录：加 `-O smart_flash=False`，或每次换一份随机数据。
